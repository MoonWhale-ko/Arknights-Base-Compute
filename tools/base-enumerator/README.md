# 기반시설 조건별 최고 배치 사전 계산기 · 실험판 3

시설 구성과 보유·스킬 해금 조건을 생성하고, 각 조건에서 지원 모델 기준 최고 배치 한 건을 저장하는 로컬 프로그램입니다. 기존 사이트에 배포하지 않았습니다.

## 시작

압축을 풀고 `standalone.html`을 브라우저에서 엽니다. **시설 자동 생성 예제 → 새 전수검사 시작**으로 작은 범위를 먼저 실행하세요. 이 예제는 생산 품목이 다른 시설 조건 2개를 검사합니다. 고정 시설 예제는 21개 배치를 검사하여 최고 결과 1건을 저장합니다.

전체 인원 자동 비교는 415개 데이터 항목의 미보유·보유 및 해금 상태를 생성합니다. 최소·최대 보유 수를 모두 10으로 설정하면 10명 조건을 생성합니다. 전체 범위 완주를 보장하지 않으며, 처음부터 전체 범위를 실행하면 매우 오래 걸립니다. 중단 버튼으로 저장한 후 재개할 수 있습니다. 브라우저 저장소를 지우면 결과가 사라지므로 NDJSON과 재개 파일을 내려받으세요.

## 계산 범위

- 제어센터 레벨별 시설 개수·레벨 제한, 발전소 1~3개, 전력 공급과 전체 시설 소비량을 반영합니다.
- 위치·층·방 번호는 구별하지 않습니다. 같은 종류·레벨·생산 품목의 시설은 전체 교대 일정이 같은 순열을 제거합니다.
- 제조소 품목은 작전기록 3종, 순금, 오리지늄 조각 제작법 2종이며 시설 레벨 해금 조건을 적용합니다.
- 근무 인원은 빈 방부터 정원까지 생성하며, 관련 해금 스킬이 있는 후보만 사용합니다. 동시 배치와 교대조의 인원 중복을 제거합니다.
- 2/3교대, 12시간/첫 소진/전원 소진, 시작 컨디션 24, 숙소 분위기와 지원 스킬을 계산합니다.
- `optimizeDormSupport`가 true이면 숙소 지원자 조합도 탐색합니다. 지원자는 전 교대 동안 고정되며 근무 인원과 중복하지 않습니다. 숙소 내 순서 및 임의의 휴식 행동 전체를 탐색하지는 않습니다.
- 첫 24시간과 모든 조가 한 번씩 근무하는 첫 사이클을 각각 시뮬레이션합니다. 사이클 미완료는 완료로 추정하지 않습니다.
- 사무실 작업량 → 미보유 단서 정책 → 응접실 속도 → 생산물 우선순위로 비교합니다. 첫 24시간 또는 첫 사이클의 시간당 값을 비교 기준으로 선택합니다.

## 시설 생성 설정

화면의 조건 JSON에서 `layoutSearch`를 변경합니다. 고정 시설 모드에서는 해당 항목을 제거하고 `base.rooms`와 `products`를 지정합니다.

```json
{"enabled":true,"controlLevels":[1,2,3,4,5],"powerCounts":[1,2,3],"factoryCount":[0,5],"tradingCount":[0,5],"dormCount":[0,4],"recipes":["1","2","3","4","13","14"],"allSupportBuilt":false,"ambience":"max"}
```

개수 범위는 양 끝을 포함합니다. `allSupportBuilt`는 개방된 우측 지원시설을 모두 건설하는 설정입니다. 숙소 수는 `dormCount`로 별도 지정합니다. 분위기는 `max` 또는 고정 숫자이며 모든 분위기 값을 자동 순회하지 않습니다. 자동 생성 모드에서는 특정 방 ID에 고정한 지원자·상주자·후보 제한을 함께 사용하지 않습니다.

## 대량 계산과 조회

Node.js 24에서 검사했습니다. 별도 패키지 설치나 서버는 필요 없습니다.

```sh
node cli.mjs --input batch-demo.json --output results.ndjson
node cli.mjs --input universal.json --output large.ndjson --seconds 60
node cli.mjs --input universal.json --output large.ndjson --seconds 60 --resume
node export-csv.mjs results.ndjson results.csv
node lookup.mjs results.ndjson my-conditions.json matched.json
node --test test.mjs batch.test.mjs
```

`--limit`은 이번 실행에서 검사할 배치 수, `--conditions`는 완료할 조건 수 제한입니다. 결과 파일과 `.checkpoint.json`을 함께 보관하세요. 조회 입력은 생성 범위가 아닌 실제 시설·보유·해금·운영 조건을 담은 JSON입니다. 버전·데이터·조건이 정확히 일치할 때만 저장된 결과를 제공합니다. 기존 사이트의 조회 UI와 연동되지는 않았습니다.

`condition-result`는 해당 조건의 전체 탐색이 끝났음을 뜻하며 최고 배치만 포함합니다. `condition-rejected`는 입력 조건 오류입니다. 중간 최고값은 체크포인트와 summary에 보관하며 완료 결과로 취급하지 않습니다. `modelOptimalityProven`은 지원 모델의 후보 탐색에 한정되고 `gameOptimalityProven`은 항상 false입니다.

## 한계

모든 특수 스킬을 지원하는 게임 완전 재현기가 아닙니다. 미지원 효과가 있는 시설별 후보를 제외하고 사유를 표시합니다. 응접실 공식은 실험적이며 실제 단서 종류별 확률은 계산하지 않습니다. 무역소 기대 수익은 생산물 순위 다음의 동률 비교에 사용하며 드론 사용은 포함하지 않습니다. 무역소는 순금 거래만 지원하고, 제조 재료 재고 제약도 모델링하지 않습니다. 휴식 인원은 다음 근무조·컨디션·ID 순의 정해진 정책으로 배치합니다. 첫 사이클 결과는 무한 반복 가능한 일일 생산량을 의미하지 않습니다.

시설은 현재 레벨·정원·선행시설·전력을 검증하지만 승급과 철거 이력을 통한 건설 가능성은 검증하지 않았습니다. 이격의 보유·육성 연동 등 계정 조건 전체도 재현하지 않습니다. 따라서 게임상 최고 효율 99% 보증 자료로 사용할 수 없습니다.

자동 검사 26개: 소규모 독립 전수검사와 대칭 제거 결과 비교, 전력·품목 해금, 중복 방지, 숙소 지원, 24시간/사이클, 중단·재개, 조건 조회 키, 번들 Worker 실행을 확인했습니다. 실제 브라우저 화면 조작 검사는 이 환경에서 수행하지 못했습니다.


## v4: 미보유 단서 정책과 고품질 주문

- 사무실 → 미보유 단서 우대 발동 시간 비율 → 응접실 속도 → 설정한 생산물 순위 → 무역소 예상 용문폐/시간 순서입니다.
- 특정 번호 단서의 확률 우대는 순위에 가산하지 않습니다. 미보유 우대는 여러 명이어도 중복 가산하지 않습니다. 보유 단서 우대도 임의 감점하지 않습니다.
- `options.missingClues`에 현재 없는 단서 번호를 입력합니다. 비었거나 7개 모두 없으면 종류 선호를 비교하지 않습니다. `options.clueExchangeActive`가 true일 때만 교류 조건 효과를 적용합니다. 단서 게시판/교류 상태는 검사 동안 고정하며 실제 단서 획득은 생성하지 않습니다.
- 고품질 주문: 3레벨의 단독 α·β, α+α, α+β 관측 분포를 사용합니다. 다른 중첩과 1/2레벨의 품질 효과는 평가 오류로 남기며 전체 최적성 증명을 하지 않습니다.
- **성숙 분포 고정·기대 작업량 근사**입니다. 첫 입실부터 α 3시간/β 5시간 후 관측된 분포를 적용합니다. 초기 확률 변화, 개별 주문 추첨·완료 시점·교대 이월은 재현하지 않으므로 첫 24시간 실제 수익이 아닙니다. 주문 수는 소수가 될 수 있습니다.
- 예상 용문폐/순금/주문을 분리하고 주문 보관 상한, 교대 시 납품, 컨디션에 따른 활성 스킬을 반영합니다. 순금 재료는 충분하다고 가정하며 제조 생산량에서 차감하지 않습니다.
- 샤마르의 동료당 효율 대체 및 테킬라의 4순금 주문 보너스를 지원합니다. 프로바이조·기타 특수 주문과 미지원 연계 스킬은 여전히 제외합니다.
- 근거: https://prts.wiki/w/罗德岛基建/贸易站 (2026-10-16 확인). 실제 게임 확률 공식이 아닌 공개 관측 자료입니다.
- 모델 버전을 v4로 올려 이전 결과/체크포인트와 혼용하지 않습니다. 자동 배포하지 않습니다.


## v5: 기대값 범위와 응접실 역할 제한

- 무역소 수익은 품질 우대 없는 기본 분포와 효과 성숙 분포를 각각 계산한 **시나리오 기대값 범위**로 표시합니다. 실제 무작위 수익의 최소·최대, 통계적 신뢰구간 또는 초기 확률 곡선에 대한 엄밀한 상하한이 아닙니다. 두 시나리오 모두 실제 결과와 다를 수 있습니다.
- 두 시나리오는 주문 보관량과 교대 납품을 독립적으로 누적합니다. 배치 순위는 기존처럼 성숙 시나리오의 기대 수익을 사용하며 결과에 `rankingBasis: mature`를 기록합니다.
- 응접실은 발동 가능한 미보유 단서 우대 담당을 최대 1명만 포함합니다. 나머지 인원은 해금된 단서 수집 속도 관련 스킬이 필요합니다. 단독 배치 전용 속도 스킬만 가진 인원은 2인 조합의 속도 담당으로 사용하지 않습니다.
- 우대 담당이 없거나 다른 우선 시설에 필요한 경우 속도 담당만의 배치도 검사합니다. 기존 사무실 우선·우대 적용 시간 우선 기준으로 최종 비교합니다. 같은 우대 스킬 두 명은 속도 효과가 함께 있어도 동시에 넣지 않습니다.
- v4 체크포인트와 결과는 버전이 달라 혼용하지 않습니다. 배포는 하지 않습니다.


## v6: 시설별 후보 재사용과 안전한 조기 중단

- 첫 실행은 소규모 고정 시설 예제로 열립니다. 실제 보유 명단의 `current` 계산이 기본 사용 경로이며, `all-operators`·시설 자동 생성은 별도 실험 모드로 유지합니다. 저장된 사용자 입력은 덮어쓰지 않습니다.
- `evaluator.mjs`: 배치 탐색과 분리된 스킬/시설 상태 평가. 동일 제어센터 인원·활성 상태의 효과를 재사용하되 실제 인원 신원은 보존합니다. 이전에 미지원이던 연계 스킬을 이 작업으로 새로 지원한 것은 아닙니다.
- `search.mjs`: 시설 종류·레벨·생산물·후보·고정 인원·해금 스킬을 키로 조합 표를 필요한 순서대로 생성합니다. 모든 인원 대안을 유지하고, 캐시에서 밀려난 항목은 재계산합니다. 한 시설의 최고 한 조합으로 고정하지 않습니다. 테이블 최대 32개, 각 2,048개 항목으로 메모리를 제한합니다.
- `options.searchStrategy`: `bounded`(기본) / `exhaustive`(기존 비교용). `bounded`는 우선 사무실·응접실 조건을 먼저 선택합니다. 알고리즘 선택은 추천 조건의 정체성과 별개이며 체크포인트의 실행 설정에는 포함됩니다.
- **조기 중단은 현재 12시간 교대의 사무실 작업량 상한만 사용합니다.** 피로·인원 경쟁을 무시하고 지원하는 최대 효과를 적용한 낙관적 상한이 현재 최고 사무실 작업량보다 낮을 때만 전체 가지를 제외합니다. 나머지 순위가 더 좋아도 사무실 우선 정책상 이길 수 없습니다.
- 상한을 검토하지 않은 사무실/제어센터 스킬 또는 첫 소진·전원 소진 교대에서는 해당 상한을 사용하지 않습니다. 제조소·무역소·숙소·중간 자원의 일반적인 상한 계산과 CP-SAT는 아직 구현하지 않았습니다.
- 결과의 `examined`는 실제 시뮬레이션한 배치 수이며 `boundPruned`는 조기 중단한 가지 수입니다. 가지 하나가 여러 전체 배치를 포함할 수 있습니다. `searchComplete`는 안전하게 제외한 가지를 포함해 탐색이 완료됐다는 뜻입니다.
- 중단/재개는 현재 최고 결과와 탐색 위치를 함께 저장합니다. v5 체크포인트와는 혼용하지 않습니다.
- 검증: `node --test test.mjs batch.test.mjs trading.test.mjs search.test.mjs` (38개). 2/3교대·24시간/사이클·세 교대 기준·재개·고품질 주문 예제에서 기준 탐색과 최고 점수 비교. 작은 조건의 모든 완성 배치에 대해 부분 배치의 사무실 상한이 실제 결과보다 낮지 않은지도 검사합니다.
- 측정 재현: `node benchmark-search.mjs search-benchmark.json`. 두 소규모 예제에서 실제 시뮬레이션 21→17건, 1,659→1,151건. 최고 점수 동일. 측정 파일에 3회 중앙 실행시간도 기록하지만 환경에 따라 달라지며 대규모 배치 성능 예측은 아닙니다.
- 전체 보유 조건을 모두 미리 저장하는 규모 문제나 미구현 특수 스킬을 해결한 버전은 아닙니다. 공개 사이트 수정·자동 배포·원격 계산 실행은 하지 않습니다.


## v7: 여러 배치를 동시에 검증

- 화면의 **동시 검증**: 자동(논리 CPU 한 개를 남기고 최대 4개) / 1 / 2 / 4 / 8. 중앙 탐색기가 중복 없는 배치를 생성하고 검증 워커에 나눠 보냅니다. 각 워커는 별도 스레드에서 컨디션·교대·생산량 시뮬레이션을 실행합니다.
- 검증 워커당 최대 16건씩 묶어서 전송합니다. 최적 결과와 순위는 중앙에서 합칩니다. 동률이면 먼저 생성된 배치를 선택하므로 응답 도착 순서가 추천을 바꾸지 않습니다.
- 같은 조건의 진행 중 작업을 모두 반영한 뒤 조건 결과 한 건을 저장합니다. 중단 요청도 현재 묶음을 끝내고 저장합니다. 체크포인트에는 미완료 작업을 남기지 않으며 다른 워커 수로 재개할 수 있습니다.
- 브라우저가 중첩 워커를 지원하지 않거나 워커가 실패하면 해당 묶음을 단일 실행으로 다시 검증합니다. 이미 반영한 결과를 중복 집계하지 않습니다. 브라우저 탭/컴퓨터를 끄면 멈추며 원격 실행은 별도입니다.
- CLI: `node cli.mjs --input examples/quality-trading.json --output results.ndjson --workers 4`. `--workers` 범위 1~8, 생략 시 CPU 수에 따라 최대 4. CLI도 같은 작업 분배·검증 기능을 사용합니다.
- 실제 병렬 실행은 `evaluation-node-worker.mjs` / `evaluation-worker.mjs`, 공통 검증은 `evaluation-jobs.mjs`, 작업 배분은 `parallel.mjs`에 있습니다. 단일 HTML에도 검증 워커 코드가 포함됩니다.
- 병렬도는 계산 속도의 배수가 아닙니다. 작은 예제에서는 준비·전송 비용으로 더 느릴 수 있고, 탐색·저장 부분은 여전히 중앙에서 처리합니다. 전체 보유 조건 수를 줄여주지는 않습니다.
- 42개 검사 통과. 실제 Node 워커 2개와 단일 실행의 최고 점수·수익 범위 비교, 병렬 중단/재개, 중복 반영 방지, 워커 실패 후 재계산, 단일 HTML의 검증 워커 실행을 검사했습니다. 별도의 CLI 확인에서도 두 모드 모두 예제 1,151건·오류 0·조건 결과 1건·동일 최고 점수였습니다.
- 실행 예산(`--seconds`, 중단 버튼)은 현재 검증 묶음이 끝난 뒤 적용되므로 약간 초과할 수 있습니다. v6 체크포인트와 혼용하지 않습니다. 배포하지 않습니다.


## GitHub 실행기 CPU에 맞춘 설정

- `resources.mjs`: `auto`는 4 vCPU에서 검증 워커 3개. GitHub 환경에서는 명시적으로 요청한 수가 할당 CPU보다 많으면 제한합니다. 실제 CPU 수와 적용 워커 수를 로그·요약에 기록합니다.
