# 시설 공통 후보 자료 확장 — 2차 실험

## 결과와 보존

기존 제조소 자료를 재사용하면서 무역소·발전소·사무실·응접실의 후보 자료를 추가했다. 이전 제조소 코드·자료·측정 파일·보고서 6개는 SHA-256을 작업 전후 비교해 모두 같은 바이트임을 확인했다. 삭제하거나 덮어쓰지 않았다. 새 파일 이름에는 `local-…-v1`을 사용했다.

과거 GitHub Actions 첨부 결과는 저장소 파일과 다르다. 기존 실행의 7일 보관 정책은 이번 작업에서 변경하지 않았으며 기간 후 자동 만료된다. 기존 원격 전수 계산이나 사이트 배포는 시작하지 않았다.

| 시설 | 지원 인원 / 해금 상태 | 저장 조합 | 생성·압축 | 압축 크기 | 미지원 해금 상태 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 무역소 | 45명 / 58개 | 31,827개 | 1.475초 | 155,793 B | 55개 |
| 발전소 | 30명 / 41개 | 42개 | 0.032초 | 3,505 B | 6개 |
| 사무실 | 23명 / 29개 | 30개 | 0.010초 | 3,972 B | 16개 |
| 응접실 | 46명 / 107개 | 5,693개 | 0.198초 | 35,466 B | 19개 |

4개 시설의 조합 합계는 37,592개이다. 이 합계는 전체 기지 배치 경우의 수가 아니다. 제어센터·숙소 프로필까지 포함한 새 압축 자료는 총 211,669바이트다. 생성과 파일 읽기·보유 조건 탐침을 포함한 전체 실험은 1.842초였다. 로컬 Linux / Node v24.19.0 측정이며 브라우저·GitHub·전체 계정의 계산 시간 예측은 아니다.

## 제어센터와 숙소

제어센터는 지원 해금 상태 42개, 숙소는 70개를 저장했다. 두 시설은 `profiles-only`로 명시하여 모든 5인 조합을 파일로 전개하지 않았다. 최종 계산 연결 실험에서는 입력한 계정의 후보만 기존 모델로 만들고, 필요한 조합을 순서대로 생성한다. 탐색 시간·배치 수 제한이 적용된다. 새 특수 연계 효과를 구현하거나 미지원 스킬을 해결한 것은 아니다.

## 보유·시설 조건 필터

- 실제 보유와 정예화·레벨로 해금한 스킬을 다시 대조한다. 오퍼레이터 신원과 다른 해금 상태를 동시에 배치하지 않는다.
- 응접실은 같은 스킬이라도 정예화가 다르면 기본 속도가 달라지므로 프로필을 구분한다. 미보유 단서 담당 최대 1명과 속도 관련 스킬 동료 정책을 적용한다. 교류 활성 상태도 구분한다.
- 무역소는 시설 레벨과 관측된 고품질 주문 중첩을 검사한다. 자료가 없는 조합은 제외 사유로 남긴다. 기존의 기본/성숙 시나리오 기댓값을 사용하며 확률적 수익 보장 구간은 아니다.
- 발전소 자료는 드론 회복 스킬의 가산 효율이다. 24시간 드론 누적 생산량과 소비를 새로 구현한 것은 아니다.
- 사무실은 숙소 레벨 합·정예 오퍼레이터가 배치된 시설 수·제어센터 임계 조건을 입력 변수로 둔다.
- 공통 효과식은 배치 인원 모두가 활동 중인 상태를 대상으로 한다. 피로·휴식·교대·생산 누적은 최종 기존 시뮬레이터가 계산한다.

## 실제 조건 하나의 최종 계산 연결

`solveLocalCatalog`는 한 사용자의 `development: current` 조건만 받는다. 이전 제조소 자료와 신규 4개 시설 자료를 읽어 후보를 고른 뒤, 서로 다른 시설 및 교대조 사이에 동일 인물이 겹치지 않게 합친다. 제어센터·숙소는 필요할 때 후보를 만들고 고정 숙소 지원자·상주자 제약은 기존 모델과 최종 시뮬레이터로 검사한다. 자동 숙소 지원자 탐색도 작은 조건에서 비교했다.

평가는 기존 사무실 → 미보유 단서 정책 → 응접실 속도 → 생산 우선순위 → 무역소 수익 순서를 그대로 사용한다. 시간 또는 배치 수 제한에 걸리면 `complete: false`를 기록한다. 이 경우 현재까지 찾은 최고값이며 최적해 증명이 아니다. 미지원 스킬 등 게임 모델 자체의 한계 때문에 `gameOptimalityProven`은 항상 false다. `modelOptimalityProven`도 제외 후보가 있으면 보수적으로 false로 둔다.

공개 소규모 검증 예제 실행:

| 항목 | 값 |
| --- | ---: |
| 검사한 전체 배치 | 1,659개 |
| 계산 오류 | 0개 |
| 자료 읽기·모델 준비 | 302.5ms |
| 탐색·최종 시뮬레이션 | 664.9ms |
| 탐색 완주 | true |

최고 점수는 기존 예제와 동일하다: 사무실 1.125, 미보유 단서 정책 1, 응접실 약 1.61, 무역소 약 792.405 용문폐/시간. 이는 기존 모델의 예제 결과 비교이며 실제 계정의 수익 보증이나 대규모 속도 검증이 아니다. 기존의 사무실 상한 가지치기를 이 실험 탐색기에 아직 연결하지 않아 예제 배치는 1,659개를 모두 검사했다. 기존 bounded 탐색은 1,151개를 검사하므로 새 방식이 무조건 더 빠르다고 주장하지 않는다.

## 검증

기존 52개와 신규 9개, 총 61개 검사 통과.

- 작은 보유 풀의 모든 부분집합과 낮은/높은 해금 설정, 시설 레벨, 교류 상태별 후보를 기존 모델 및 독립 부분집합 열거와 비교.
- 각 시설의 모든 단독 배치와 표본 다인 조합을 제어센터·숙소 분위기·정예 시설 수·누적 근무 시간의 여러 조건에서 기존 효과 계산기와 대조.
- 응접실 정예화 기본 속도 보존, 단서 담당 중복 제한, 미지원 고품질 주문 중첩 처리.
- 여러 시설의 2/3교대와 첫 소진/전원 소진/12시간 교대에서 작은 풀의 전체 배치 수 및 최고 점수를 기존 전수검사와 비교.
- 기존 제조소 자료를 신규 탐색기에 연결하고 제어센터·숙소 고정/자동 지원자를 포함한 작은 조건 비교.
- 탐색 제한 도달 시 미완료 표시, 이격 등 동일 인물 중복 방지, 압축 복원 및 오래된 자료 거부, 이전 파일 보존.

## 남은 작업

미지원 스킬, 실제 게임 규칙의 독립 검증, 큰 보유 풀에서의 초기 추천 생성·안전한 가지치기·탐색 순서 개선, 전체 24시간/사이클 성능 검증, 브라우저 연동은 남아 있다. 제어센터·숙소의 모든 외부 연계를 새로 해결한 완성품이나 최고 효율 99% 보장 버전은 아니다.

## 실행

새 자료 생성은 기존 파일을 덮어쓰지 않는다. 새로운 출력 폴더를 지정한다.

```bash
cd tools/base-enumerator
node facility-precompute-cli.mjs --output-dir new-local-catalog
```

저장소에 포함된 기존 제조소 자료와 새 자료를 함께 사용해 실제 조건 하나를 계산한다. 실행 결과 파일도 새 이름을 지정한다.

```bash
node facility-search-cli.mjs --input examples/quality-trading.json --output my-new-result.json --seconds 10 --limit 100000
```

개인 계정 조건 파일을 지정하면 해당 조건으로 계산한다. 자동 업로드·공유·GitHub 실행 호출은 없다. CLI 시간 제한은 자료 읽기/모델 준비와 별도의 탐색 예산이며, 실행 중인 최종 시뮬레이션 한 건은 마친 뒤 제한을 확인하므로 조금 초과할 수 있다.

```bash
node --test test.mjs batch.test.mjs trading.test.mjs search.test.mjs parallel.test.mjs resources.test.mjs factory-precompute.test.mjs facility-precompute.test.mjs
```

측정 원본: [LOCAL-CATALOG-EXPANSION.json](LOCAL-CATALOG-EXPANSION.json). 예제 결과: [local-search-example-v1.json](local-search-example-v1.json).
